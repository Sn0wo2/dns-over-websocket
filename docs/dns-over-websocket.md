# DNS over WebSocket 协议草案

## 1. 协议目标

通过持久化 WebSocket 连接并发传输 DNS 查询与响应, 避免为每次查询单独发起 HTTP 请求

v1 仅支持客户端发起查询、服务端返回结果; 不支持服务端主动推送、订阅、取消查询及跨连接恢复

## 2. 传输与握手

协议基于标准 WebSocket, 默认路径为 `/ws-dns-query`, 使用子协议标识 `v1.dns-ws`

- 客户端必须在握手请求中携带 `Sec-WebSocket-Protocol: v1.dns-ws`
- 服务端接受连接时, 必须选择该子协议, 并在升级响应中返回 `Sec-WebSocket-Protocol: v1.dns-ws`
- 服务端不支持请求的子协议时, 必须在升级前返回 HTTP 400
- 服务端未选择 `v1.dns-ws` 时, 客户端必须终止连接

  示例地址:

```text
wss://example.com/ws-dns-query
```

## 3. 握手鉴权

鉴权在 WebSocket 升级前完成, 成功后对当前连接持续生效

服务端可配置以下匹配条件; 配置多个条件时, 所有条件必须同时满足

| 条件     | 匹配规则                                                 |
| -------- | -------------------------------------------------------- |
| `path`   | 与配置的 URL pathname 精确匹配, 不包含 query             |
| `query`  | 指定参数必须恰好出现一次, URL 解码后的值与配置值精确匹配 |
| `header` | 指定请求头的值与配置值精确匹配                           |

匹配规则:

- `path` 不进行额外的百分号解码, 不将尾部斜杠视为等价
- `query` 参数名区分大小写, 忽略未配置的其他参数
- 鉴权 `header` 应使用单值字段, 不依赖重复请求头的合并行为

  鉴权失败时:

- `path` 不匹配: 返回 HTTP 404
- `query` 或 `header` 鉴权失败: 返回 HTTP 403, 不披露具体失败条件

  安全要求:

- 不得在日志中记录完整 `query`、鉴权请求头或凭据
- 秘密值必须使用恒定时间比较
- 通常应优先通过 `header` 传递鉴权凭据

## 4. 消息格式

协议不维护跨连接的请求状态, 使用 JSON 封装 DNS 报文

DNS 报文采用标准 DNS wire format, 通过 `dns` 字段进行 Base64URL 编码, 遵循 RFC 4648 的 URL-safe 字母表, 不包含 `=` padding, 不添加 DNS-over-TCP 的两字节长度前缀

WebSocket 消息必须使用文本帧, 每条消息包含一个完整的 JSON 对象

### 4.1. 查询 (客户端 → 服务端)

```json
{
  "id": 42,
  "dns": "AAABAAABAAAAAAAAB2V4YW1wbGUDY29tAAABAAE"
}
```

| 字段  | JSON 类型 | 说明                                                         |
| ----- | --------- | ------------------------------------------------------------ |
| `id`  | `number`  | 客户端分配的 Request ID, 必须为 `0..4294967295` 范围内的整数 |
| `dns` | `string`  | Base64URL 编码的 DNS 查询报文, 解码后长度为 `12..65535` 字节 |

两个字段均为必填, 不允许 `null`, 不进行字符串与数字之间的隐式类型转换

### 4.2. 结果 (服务端 → 客户端)

```json
{
  "id": 42,
  "status": "SUCCESS",
  "dns": "AACBgAABAAAAAAAAB2V4YW1wbGUDY29tAAABAAE"
}
```

| 字段     | JSON 类型 | 说明                                                   |
| -------- | --------- | ------------------------------------------------------ |
| `id`     | `number`  | 必填, 遵循查询 ID 的规则, 必须与对应查询一致           |
| `status` | `string`  | 必填, 区分大小写, 取值见下表                           |
| `dns`    | `string`  | 仅成功时必填; 错误时必须省略, 不允许 `null` 或空字符串 |

状态定义:

| `status`           | 含义              | `dns`                                                    |
| ------------------ | ----------------- | -------------------------------------------------------- |
| `SUCCESS`          | 成功获得 DNS 响应 | Base64URL 编码的 DNS 响应, 解码后长度为 `12..65535` 字节 |
| `INVALID_QUERY`    | 查询无效          | 省略                                                     |
| `UPSTREAM_FAILURE` | 上游失败          | 省略                                                     |
| `TIMEOUT`          | 查询超时          | 省略                                                     |
| `OVERLOADED`       | 并发或资源超限    | 省略                                                     |
| `INTERNAL_ERROR`   | 内部错误          | 省略                                                     |

错误结果仅包含 `id` 和 `status`, 不传输内部错误详情

`SUCCESS` 表示成功获得 DNS 响应, 与 DNS RCODE 无关; `NXDOMAIN`、`SERVFAIL`、`REFUSED` 等合法 DNS 响应均使用 `SUCCESS`

## 5. 并发与请求生命周期

同一连接允许多个查询并发执行, 服务端可按任意顺序返回结果

- Request ID 仅在当前连接内有效, 不同未完成查询的 ID 必须唯一
- 推荐客户端使用自增 ID
- DNS 报文自身的 16 位 Transaction ID 不参与通道层请求关联; 并发查询可以使用相同的 DNS Transaction ID
- 请求与结果通过 `id` 关联, 不依赖发送或接收顺序

## 6. 校验与错误处理

### 6.1. 查询级错误

对于 JSON 结构合法且 Request ID 未重复的查询, 出现以下情况时, 服务端必须返回 `INVALID_QUERY`, 并保持连接可用:

- `dns` 包含无效的 Base64URL 编码
- 解码后的 DNS 报文长度不在 `12..65535` 字节范围内
- DNS 报文内容不合法
- DNS 报文超出服务端配置的长度限制
